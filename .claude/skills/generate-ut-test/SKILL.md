# 単体テスト設計書からのテストコード生成スキル

単体テスト設計書 CSV（`ut-test-design.csv`）の1行=1テストケースを、対応するモジュール設計書
（`docs/module/{module}_design.md`）の関数シグネチャ・仕様と突き合わせ、
**pytest のパラメタライズドテスト**として実装するスキルです。

このスキルがやるのは「**CSV読み込み → 設計書との突合 → テストコード生成 → 実行して結果報告**」まで。
**テスト対象モジュール本体（プロダクトコード）の実装は行いません。**
設計書に書かれていない挙動を推測してテストの期待値を作ることもしません（→ 「やらないこと」）。

## 前提とするフォルダ構成/

対象フォルダ（ユーザーが指定する。例: `development/.../381_変換内容の欠落を保証する方針を定める`）配下:

```
{対象フォルダ}/
├── docs/
│   ├── design.md                    … 基本設計（パッケージ名・モジュール構成の出典）
│   ├── module/
│   │   └── {module}_design.md       … モジュール設計書（関数一覧・シグネチャ・フロー）
│   └── test/
│       └── ut-test-design.csv       … 単体テスト設計書（1行=1ケース）
└── tests/
    └── {package}/
        └── test__{module}.py        … 生成先（`test__` はアンダースコア2つ）
```

- パッケージ名（`tests/` 直下のフォルダ名）は `docs/design.md` のモジュール構成から取る。
  既存の `tests/` にフォルダがあればそれに合わせる。
- 生成先ファイル名は `test__{module_name}.py`。`module_name` は CSV の `module_name` 列の値。

## ut-test-design.csv の形式

| 列                | 内容                                                             |
| ----------------- | ---------------------------------------------------------------- |
| `id`              | ケース番号。テスト関数の `pytest.param(id=...)` の先頭に使う     |
| `module_name`     | 対象モジュール名。生成先ファイルを決める                         |
| `function_name`   | 対象関数名。1関数につき1つのテスト関数を作る                     |
| `constraint_id`   | そのケースが確かめる、設計書の同じ関数の `- 制約` の番号。カンマ区切りで複数、空欄あり。行末コメントに使う（→ 「値の書き起こし方」） |
| `argument`        | `引数名=値` 形式。複数はカンマ区切り（例: `line="...", strip_bullet=False`） |
| `expected_result` | 期待結果。リテラルとは限らない（→ 「期待結果の読み方」）         |
| `description`     | ケースの意図。`pytest.param(id=...)` とコメントに使う            |

## 進め方

### Step1. 対象を確定する

1. ユーザーが指定したフォルダを確定する。**推測で決めない。曖昧なら確認する。**
2. `docs/test/ut-test-design.csv` の存在を確認する。無ければその旨を伝えて止める。
3. CSV の `module_name` を集計し、**どのモジュールのテストを作るか**を確定する。
   複数モジュールが含まれていて依頼で絞られていない場合は、全モジュール分を生成する
   （モジュールごとに別ファイル）。

### Step2. CSV を読み込み、検算する

CSV は素直に読める形とは限らないので、読んだあと必ず以下を確認する。

- **列が揃っているか**（`id,module_name,function_name,constraint_id,argument,expected_result,description`）。
  `constraint_id` 列が無い古い形式の CSV でも生成は続け、列が無いことを報告する。
- **`constraint_id` の番号が、設計書のその関数の `- 制約` に実在するか**（Step3 で設計書を読んだ後に確認する）。
  実在しない番号は書き換えずに報告する。
- **`id` の重複・欠番**。重複していたら勝手に振り直さず、**両方を生成した上で報告する**
  （`id=` は `16a_...` `16b_...` のように接尾辞で衝突を避ける）。
- **クォートの壊れ**。CSV 内に `"` を含むケースが多く、行が途中で切れていることがある。
  行数と `id` の連番が合わない場合は該当行を提示して確認する。
- `function_name` ごとに行をグループ化する。**この単位が1つのテスト関数になる。**

### Step3. モジュール設計書を読む

`docs/module/{module_name}_design.md` を読み、関数ごとに以下を押さえる。

- **シグネチャ**（引数名・型・デフォルト値・戻り値の型）
- **戻り値の意味**。特に `str | None` を返す関数は、**どんなときに `None` を返すか**
- **フロー**（置換表・除去対象の一覧など、期待値の根拠になる記述）
- **制約**（番号付き。CSV の `constraint_id` が指す先）

ここで、**CSV の行が参照している関数が設計書に載っていない／節が空**というケースがある
（設計書の作成途中でよく起きる）。その場合は次のように扱う。

- 関数一覧の表にシグネチャがあれば、それを根拠に使ってよい。
- 挙動の記述が無く、CSV の `expected_result` だけでは期待値が一意に決まらない行は、
  **推測で埋めない**。Step5 の「要確認」に回す。

### Step4. 期待結果の読み方を判定する

`expected_result` は自然言語混じりなので、行ごとに次のどれかに分類してからコードにする。

| 分類             | CSV の書かれ方の例                                  | 生成するアサーション                                  |
| ---------------- | ---------------------------------------------------- | ----------------------------------------------------- |
| リテラル         | `"id123"` / `3` / `0`                                | `assert actual == "id123"`                            |
| None             | `None`                                               | `assert actual is None`                               |
| 他呼び出しと同値 | `normalize("○") と同じ結果になる`                    | `assert normalize("〇") == normalize("○")`            |
| 性質（冪等性等） | `normalize(normalize(text)) == normalize(text)`      | その式をそのまま `assert` する                        |
| 変化しない       | `"データー" のまま`                                  | `assert actual == "データー"`                         |
| 残る             | `"項目名" が残る`                                    | 設計書から戻り値が一意に決まるなら等価、決まらなければ包含 |
| 残らない         | `内容テキストが残らない`                             | 設計書から `""` か `None` か確定させる。**確定できなければ要確認** |

- 「残る／残らない」系は、**等価アサート（`==`）を第一候補**にする。
  設計書に戻り値の完全な形が書かれていて一意に決まる場合のみ `==` を使う。
- 一意に決まらない場合のみ `in` / `not in` による包含アサートにし、
  **その行を「要確認」として記録する**（弱いアサーションで通してしまうのを隠さない）。
- 「残らない」で `""` と `None` のどちらかが確定しない場合は、
  弱いアサートを書かずに **要確認に回し、その行はコード生成を保留する**。

### Step5. テストコードを生成する

以下の規約に従う。既存の `tests/` にファイルがある場合は、**上書き前に既存内容を読み、
手で追記された部分が無いかを確認してから**書く。

#### ファイルの骨格

```python
"""{module_name} の単体テスト

対象: {対象フォルダからの相対パス}/docs/module/{module_name}_design.md
設計: {対象フォルダからの相対パス}/docs/test/ut-test-design.csv
"""

import pytest

from {package}.{module_name} import {使う関数をカンマ区切り}
```

#### テスト関数の規約

- **1関数につき1つのテスト関数**。名前は `test_{function_name}`。
  性質テスト（冪等性など）のように形が違うケースは `test_{function_name}_{観点}` として分ける。
- **テスト関数名は必ず英語（ASCII）で書く。日本語を混ぜない。**
  `{観点}` も英語にする。対応の例:

  | 観点         | 関数名の例                            |
  | ------------ | ------------------------------------- |
  | 冪等性       | `test_normalize_idempotent`           |
  | 同値になる揺れ | `test_normalize_equivalent_variants`  |
  | 異常系       | `test_normalize_invalid_input`        |
  | 境界値       | `test_count_occurrences_boundary`     |
  | 別形を作らない | `test_drop_enumerator_returns_none`   |

  日本語で意図を伝えるのは **docstring と `pytest.param` の `id`** の役割とし、関数名には持ち込まない
  （`pytest -k` での絞り込み、CI のログ、JUnit XML などで日本語の関数名は扱いにくいため）。
- `@pytest.mark.parametrize` を使い、各ケースは `pytest.param(...)` で書く。
- `pytest.param` の `id` は **`"{csv_id}_{description}"`**。
  日本語はそのまま入れてよい（既存テストがそうなっている）。
  `id` 内の空白・カンマ・括弧は pytest の出力が読みにくくなるので `_` に寄せる。
- パラメータ名は **CSV の `argument` の引数名をそのまま使う**。期待値側は `expected_{引数名}`
  ではなく `expected` を基本とする。
- CSV に無いケースを勝手に足さない。**CSV の行数とテストケース数を一致させる。**

#### 値の書き起こし方

- `argument` の `引数名=値` を **キーワード引数として解釈**し、値だけをパラメータに渡す。
  値が複数ある行（例: `line="...", strip_bullet=False`）は、その関数のテスト関数の
  パラメータを引数の数だけ持たせる。**一部の行にしか出てこない引数は、
  設計書のデフォルト値を明示的に書いて全行に持たせる**（行ごとに引数数が変わるのを避ける）。
- `\n` `​` `­` `﻿` などのエスケープは、**Python の通常文字列としてそのまま書く**
  （raw 文字列にしない）。CSV 上の `\\|` のような二重エスケープは、
  Markdown のエスケープ記法 `\|` を意味するので `"A\\|B"` と書く。
- `"～"(U+FF5E)` のように**コードポイント注記が付いている値**は、
  注記を値に含めず `"～"` のようにエスケープで書き、行末コメントで注記を残す。
  見た目が同じで別コードポイントの文字（`〇` `○` `◯`、`～` `〜` など）は
  **必ずエスケープ表記**にする。ソース上で判別できなくなるため。
- `constraint_id` が空でない行は、`pytest.param(...)` の閉じ括弧の後ろに **`# 制約: 3,4`** の形で行末コメントを付ける
  （設計書の制約から該当ケースを検索できるようにするため）。空欄の行には付けない。
  `pytest.param` の `id` には含めない（`"{csv_id}_{description}"` のまま）。

#### 生成例（実際の CSV から）

```python
@pytest.mark.parametrize(
    "text, expected",
    [
        pytest.param(
            "ＩＤ１２３",
            "id123",
            id="1_全角英数字がNFKCで半角化される",
        ),
        pytest.param(
            "実績 手入力\n（原材料）",
            "実績手入力(原材料)",
            id="4_半角空白・全角空白・改行・タブを除去する",
        ),  # 制約: 2
    ],
)
def test_normalize(text, expected):
    assert normalize(text) == expected


@pytest.mark.parametrize(
    "text, reference",
    [
        pytest.param("〇", "○", id="5_丸記号の揺れを代表文字に寄せる"),   # 〇 / ○
        pytest.param("◯", "○", id="6_丸記号の揺れ_別コードポイント"),    # ◯ / ○
    ],
)
def test_normalize_equivalent_variants(text, reference):
    assert normalize(text) == normalize(reference)


@pytest.mark.parametrize(
    "text",
    [
        pytest.param("Ａ－１ 区分　（○）", id="15_正規化を2回適用しても結果が変わらない"),
    ],
)
def test_normalize_idempotent(text):
    assert normalize(normalize(text)) == normalize(text)
```

### Step6. 実行して結果を報告する

1. 生成後、対象フォルダで `python -m pytest tests/{package}/test__{module}.py -q` を実行する。
2. **テスト対象モジュールが未実装の場合、収集エラー（ImportError）になるのが正常**。
   これを「失敗」として隠さず、「実装前なので import で落ちている」と明示して報告する。
   この状態を取り繕うために、モック・スタブ・空実装を勝手に作らない。
3. 実装済みで失敗した場合は、**テストコード側の書き起こしミスか、実装の不備か**を切り分けて報告する。
   設計書と CSV が根拠なので、**テストの期待値を実装に合わせて書き換えて通すことはしない。**

最後に次を報告する。

- 生成したファイルと、CSV 行数 / 生成ケース数（一致していること）
- **要確認リスト**: 設計書から期待値が一意に決まらなかった行（`id` と理由）
- CSV 側の不備（`id` 重複・欠番・クォート崩れ・設計書の制約に実在しない `constraint_id` など）
- pytest の実行結果

## やらないこと

- **テスト対象モジュール本体の実装**。テストコードの生成までに留める。
- **設計書に無い挙動の推測**。期待値が決まらない行は要確認に回す。それらしいアサートで埋めない。
- **CSV や設計書の書き換え**。不備を見つけたら報告するだけにする
  （ユーザーが直すと判断した場合のみ、依頼を受けてから直す）。
- **CSV に無いテストケースの追加**。網羅性が足りないと感じた場合は、
  コードに足さず「設計書に追加すべきケース」として提案する。
- **通すためのアサーションの弱体化**。落ちるなら落ちたまま報告する。
