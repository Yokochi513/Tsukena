# モジュール設計書からの単体テストケース作成スキル

関数モジュール型のモジュール設計書（`docs/module/{module}_design.md`）を読み、
**各関数のテストケースを洗い出して** 単体テスト設計書 CSV（`docs/test/ut-test-design.csv`）に追記するスキルです。
特定の言語・テストの仕組みを前提にしません。引数や期待値の値の書き方は、基本設計で決めた言語に合わせます。

このスキルがやるのは「**設計書を読む → 関数ごとにテスト観点を洗い出す → 期待値を設計書から確定させる → CSV に追記 → 制約との対応を確認して報告**」まで。
**テストコードもプロダクトコードも書きません。** テストコードは後工程（スキルまたは人）が、この CSV を入力にして作ります。
設計書から期待値が一意に決まらないケースを、推測で埋めることもしません（→ 「やらないこと」）。

## 用語

| 用語                 | 意味                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| モジュール           | 責務の単位。言語に応じてパッケージ・名前空間・クラス・ファイルなどに読み替える                       |
| 関数                 | 処理の単位。言語に応じてメソッド・手続きなどに読み替える                                             |
| 採用言語             | `docs/design.md` の決定事項（言語・実行環境）に書かれた言語。値のリテラル・型・命名の表記はこれに従う |
| 公開関数／非公開関数 | モジュールの外から呼ばれる関数／モジュールの中だけで使う関数。見分け方は採用言語の慣習に従う         |
| データ定義の設計書   | 受け渡すデータ構造を定義したモジュールの設計書（データ定義モジュール型。例: `model_design.md`）      |
| テストのルート       | テストコードを置くフォルダ。`docs/design.md` のモジュール構成に書かれたもの                         |
| 後工程               | この CSV を入力にテストコードを作る工程（スキルまたは人）                                            |

## 前提とするフォルダ構成

対象フォルダ（ユーザーが指定する。指定が無ければリポジトリのルート）配下:

```
{対象フォルダ}/
├── docs/
│   ├── design.md                    … 基本設計（モジュール間の前提・採用言語の出典）
│   ├── adr/
│   │   └── 000N-*.md                … 設計判断の記録
│   ├── module/
│   │   ├── {module}_design.md       … ★このスキルの入力（関数モジュール型）
│   │   └── model_design.md          … 受け渡すデータ構造と不変条件（データ定義の設計書）
│   └── test/
│       └── ut-test-design.csv       … ★このスキルの出力先（1行=1ケース）
└── {テストのルート}/                 … 後工程の生成先。このスキルでは触らない
```

入力の設計書は `generate-module-design` スキルのテンプレート
[`../generate-module-design/templates/function_module.md`](../generate-module-design/templates/function_module.md)
の構成で書かれていることを前提とする。**テスト観点はこのテンプレートの節から機械的に洗い出す**（→ Step3）。

データ定義モジュール型（`model` など、`## データ構造一覧` を持つもの）は対象外とする。
依頼された場合はその旨を伝え、不変条件の検査を関数のケースとして書くかどうかをユーザーに確認する。

`.claude/skills/` に後工程のスキルがある場合は、そのスキルが読む列・書き方を Step2 で確かめ、合わせて書く。

## ut-test-design.csv の形式

| 列                | 内容                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `id`              | ケース番号。**CSV 全体で通し番号**（モジュールをまたいで連番）。既存の最大値 + 1 から振る     |
| `module_name`     | 対象モジュール名（ファイルの拡張子を付けない）                                                |
| `function_name`   | 対象関数名。設計書のシグネチャと一字一句同じにする（非公開関数もシグネチャの名前のまま書く）  |
| `constraint_id`   | そのケースが確かめる制約の番号（→ 「constraint_id の書き方」）。制約に関係しないケースは空欄  |
| `argument`        | `引数名=値` をカンマ区切り。値は採用言語のリテラルで書く（→ 「argument の書き方」）            |
| `expected_result` | 期待結果。後工程が読める決まった形で書く（→ 「expected_result の書き方」）                    |
| `description`     | ケースの意図。**何を確かめるか**を1文で。根拠が必要なら括弧で添える                           |

ファイルの形式は既存に合わせる。新しく作る場合は **UTF-8（BOM なし）・CRLF・ヘッダー行あり・必要な列だけダブルクォートで囲む** とする。

## 進め方

### Step1. 対象を確定する

1. 対象フォルダと**対象モジュール名**を確定する。**推測で決めない。曖昧なら確認する。**
2. `docs/module/{module}_design.md` を確認する。
   - 無い、または空ファイル（0バイト）の場合は止めて、先に `generate-module-design` で設計書を書くよう伝える。
   - `## 関数詳細` を持たない（データ定義モジュール型）場合は、前述のとおり確認する。
3. `docs/test/ut-test-design.csv` を読み、次を把握する。
   - **既存の `id` の最大値**（新しいケースはその次から振る）
   - **対象モジュールの既存行があるか**。ある場合は「追加モード」になる（→ Step6）
   - 書式の実例（`argument` / `expected_result` の書かれ方）。**既存と同じ書き方にそろえる**
   - CSV が無い場合は、上の形式でヘッダー行から作る。

### Step2. 入力を読む

書き始める前に、少なくとも次を読む。読まずに書かない。

| 入力                                  | そこから取るもの                                                                 |
| ------------------------------------- | -------------------------------------------------------------------------------- |
| `docs/design.md` 決定事項             | **採用言語**。`argument` / `expected_result` の値のリテラルの書き方              |
| 対象の `{module}_design.md`           | 関数一覧・シグネチャ・引数一覧・返り値一覧・詳細・制約・フロー・方針の節・定数   |
| データ定義の設計書                    | 戻り値のデータ構造のフィールド名と不変条件（期待値に書くフィールド名の出典）     |
| 依存先モジュールの設計書              | 呼び出す関数（`normalize()` など）の結果。**期待値を具体値で書くために必要**     |
| `docs/adr/*.md`（参照先のみ）         | 設計書が根拠として参照している決めごと                                           |
| 既存の `ut-test-design.csv`           | 既存ケースの粒度・書き方・隣接モジュールで既に確かめている観点                   |
| `.claude/skills/*/SKILL.md`（あれば） | 後工程が前提にしている CSV の読み方                                              |

採用言語が `docs/design.md` からも設計書のシグネチャ・既存の CSV からも決まらない場合は、**推測で決めずにユーザーに確認する**。

依存先の関数を通した結果を期待値に書く場合（例: 正規化後の文字列）は、**依存先の設計書のフロー・対応表から一意に導けること**を確認する。
導けなければ「`normalize("○")` と同じ結果になる」のような**同値の形**で書く（→ 「expected_result の書き方」）。

### Step3. 関数ごとにテスト観点を洗い出す

関数一覧の**上から順に（呼び出し階層順）**、1関数ずつ観点を出す。
観点はテンプレートの節から次の対応で拾う。**全関数について全行を当てはめ、当てはまらないものだけを飛ばす。**

| 設計書の節                          | 拾う観点                                                                                              | 最低限のケース                                         |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `- 引数一覧` / `- 返り値一覧`       | 典型的な入力で、返り値の型・内容のとおりに返るか                                                      | 1件（正常系の代表）                                    |
| `- フロー` の各手順                 | その手順の処理が行われたことが結果に現れるか                                                          | **手順1つにつき1件以上**                               |
| `- フロー` の分岐（「〜の場合」）   | 分岐の両側。条件を満たす入力と満たさない入力                                                          | 分岐1つにつき2件（真側・偽側）                         |
| `- フロー` の最後の境界・異常の手順 | 空入力・0件・見つからない・対象外の条件・例外                                                         | **書かれている条件1つにつき1件**                       |
| 除外条件・しきい値（「4桁以上」等） | 境界値。しきい値のちょうど・1つ手前                                                                   | 境界の両側で2件                                        |
| `順序の理由`                        | 順序を入れ替えると結果が変わる入力（その順序でしか正しくならないもの）                                | 理由1つにつき1件                                       |
| フロー後の対応表                    | 表の各行（置換表・除去対象・識別子の一覧）                                                            | **表の1行につき1件**。同じ規則の行は代表でまとめてよい |
| `- 制約`                            | 1項目ずつ、守られていることを確かめる（→ Step4）                                                      | **制約1項目につき1件以上**（テスト不能なものを除く）   |
| `- 詳細` の入出力の性質             | 決定的（同じ入力を2回）・冪等（2回適用）・順序保持・入力と同じ長さ・引数を変更しない                  | 性質1つにつき1件                                       |
| `- 詳細` の既知の制約・補正しない点 | 「補正しない」「既知の制約」と書かれた挙動が、そのとおりになっていること（仕様として固定するため）    | 1件                                                    |
| `## 〇〇の方針` の節                | その関数の詳細からアンカーリンクで参照している方針の行（数えるもの・数えないもの）                    | 表の1行につき1件                                       |
| `### モジュール冒頭に置く定数`      | 定数の各値で判定が変わること。定数に無い値は対象外になること                                          | 値1つにつき1件 + 定数に無い値1件                       |

- 観点を出したら、**同じことを確かめているケースをまとめる**。1ケースで2つの観点を満たせるなら1件でよい
  （例: 空入力のケースが制約「例外にしない」も兼ねる）。ただし description は主たる観点で書く。
- 入口の関数（公開関数）では、下位関数で確かめた細かい規則を繰り返さない。
  **下位関数を組み合わせた結果**（受け渡し・入力順・ファイル読み込み・例外の伝わり方）を中心にする。
- 他モジュールの責務（「〜は`validator`が行う」）をこの関数のケースにしない。

### Step4. 制約とケースを対応させる

`- 制約` は**後工程のテスト観点として1項目ずつ確かめられるように書かれている**。全項目について次を行う。

1. その制約を確かめるケースを Step3 の中から探す。無ければ足す。
2. 「〜を持たない」「〜しない」のように、**その関数単体では確かめにくい否定の制約**は、観測できる形に裏返して扱う。
   - 観測できる形に言い換えられるもの（「引数を変更しない」→ 呼び出し後に引数が元のままか）は、そのままケースにする。
   - 判定や処理を依存先に任せている制約（「行の種別の判定を持たない」など）は、
     **依存先を呼び出し、その戻り値をそのまま使う**形に裏返す
     （例: 「`classifyLine()` に行を渡し、その戻り値をそのまま使う」）。
     ケースは依存先をモック（テストダブル）に差し替え、**本関数だけでは出てこない戻り値**を返させて、結果がそれに従うことと、呼び出しの引数・回数を確かめる。
     「呼び出していること」だけを確かめると、呼んで戻り値を使わない実装を見逃すため、戻り値の使われ方まで確かめる。
   - 特定の処理をしない制約（「連番を落とした形は作らない」など）は、**その処理の関数を呼ばない**形に裏返し、
     スパイで呼び出し回数が0であることを確かめる。
   - 依存先の差し替えが採用言語・テストの仕組みで難しい場合（差し替えの口が設計書に無い等）は、その旨を報告に挙げる。
   - 裏返すと設計書の制約の文言が変わるため、**設計書は書き換えずに、言い換えの案を報告に挙げる**。
     ユーザーの了承を得てから、制約の文言の書き換えとケースの追加を行う。
3. 裏返しても観測できない制約（「値が正しいかの判断は行わない」など、モジュール間の責務の境界そのもの）は、
   **無理にケースを作らず「対応ケースなし」とする**（その制約の番号はどの行の `constraint_id` にも現れない）。
   関数の制約ではなくモジュールの責務なので、制約から外して `## 背景・目的` / `## 依存関係` に書くことを報告で提案する。
   制約から外す場合は、その関数の正常系の代表ケース（戻り値が抽出・変換の結果だけであること）で責務を確かめる。
4. 対応するケースの `constraint_id` 列に、その制約の番号を書く（→ 「constraint_id の書き方」）。
   **制約ごとの対応表を Step8 の報告に必ず載せる。**

制約とケースの対応は **CSV の `constraint_id` 列だけで持つ**。設計書の制約側にテストIDは書かない。

### Step5. ケースを CSV の行に書き起こす

#### argument の書き方

- `引数名=値` をカンマ区切りで書く（例: `lines=["本文"], kinds=["本文"]`）。値は **採用言語のリテラル**で書く。
  - 文字列はダブルクォート（採用言語の文字列リテラルがダブルクォートでない場合はその表記）。制御文字・見分けにくい文字はエスケープ（`\n` `​` `　` など、採用言語の表記）で書く。
  - 見た目が同じで別コードポイントの文字（`〇` `○` `◯`、`～` `〜` など）は、値の後ろに `(U+FF5E)` のように注記する。
  - データ構造はデータ定義の設計書の定義に沿い、採用言語で生成する形で書く（例: `Row(line=1, value="abc")`）。
    期待値に効かないフィールドは省略してよい。
  - シグネチャの型が区別している入れ物の種類（配列と固定長の組、変更できる列とできない列など）は、値の書き方でも区別する。
- **必須の引数はすべて書く。** 期待値に影響しない引数でも、代表値（`path="a.txt"` など）を入れる。
  既存の行で省略されているものは書き換えない（→ 「やらないこと」）。
- 任意の引数（デフォルト値あり）は、そのケースで既定値以外を使う場合だけ書く。
- リテラルで書けない前提（ファイルの中身・存在しないパス・呼び出し方）は、値の後ろに全角括弧で補足する。
  - `paths=["a.txt"]（内容="見出し\r\n本文\r\n"）`
  - `paths=["missing.txt"]（存在しないパス）`
  - `同じpathsで2回呼ぶ`（性質のケース）
  - `（classifyLineを戻り値"見出し"のモックに差し替えて呼ぶ）`（依存先の差し替え。→ Step4）
  - `（dropEnumeratorを呼び出しを記録するスパイに差し替えて呼ぶ）`（呼び出しの記録。→ Step4）
  - `（ALLOWED_HOSTSをexample.orgだけに差し替えて呼ぶ）`（定数を参照していることの確認）

#### expected_result の書き方

後工程がアサーションに変換できる形だけを使う。**自然言語の説明文だけの期待値は書かない。**
値のリテラルは `argument` と同じく採用言語で書く。

| 形               | 書き方の例                                                  | 使う場面                                                  |
| ---------------- | ----------------------------------------------------------- | --------------------------------------------------------- |
| リテラル         | `"id123"` / `3` / `[]`                                      | 戻り値全体が一意に決まるとき（**第一候補**）              |
| 真偽             | `真` / `偽`                                                 | 真偽値を返す関数                                          |
| 値なし           | 採用言語で値が無いことを表すリテラル（`null` など）         | 値が無いことを返すのが仕様のとき                          |
| フィールドの列挙 | `len==1, [0].kind=="見出し", [0].line==1`                   | 戻り値がデータ構造で、確かめたいフィールドが一部のとき    |
| 他呼び出しと同値 | `normalize("○") と同じ結果になる`                           | 依存先の結果を具体値で書くと根拠が二重になるとき          |
| 性質の式         | `normalize(normalize(text)) == normalize(text)`             | 冪等性など、式でしか書けないとき                          |
| 呼び出しの比較   | `1回目と2回目の戻り値が一致する`                            | 決定的であることを確かめるとき                            |
| 依存先の呼び出し | `classifyLineが"本文"を引数に1回だけ呼ばれる` / `dropEnumeratorが1回も呼ばれない` | 依存先をモック・スパイに差し替えたケース（→ Step4）。戻り値の確認と組み合わせる |
| 変化しない       | `そのまま返る` / `"データー" のまま`                        | 入力を加工しないことを確かめるとき                        |
| 例外（エラー）   | `例外が送出される`（型が設計書にあれば `{例外の型} が送出される`。エラーを戻り値で返す言語では `エラーが返る`） | フローに例外・エラーを返すと書かれているとき |

- **「〜が残る」「〜が残らない」は、設計書から戻り値が一意に決まる場合はリテラルで書く。**
  一意に決まらない場合だけ「残る」形で書き、報告の要確認に挙げる（後工程で包含アサートになり弱くなるため）。
- 「内容が残らない」のように、空文字と値なしのどちらか決まらない書き方はしない。設計書から確定させる。
  確定できなければ、その行は書かずに要確認に回す。
- 1ケースの期待値は1つの結果について書く。「AかつB」を書くならフィールドの列挙の形にする。

#### description の書き方

- **何を確かめるか**を1文で書く（例: 「行が無い場合は空の列を返す」）。
- 観点の根拠が設計書の詳細・方針にある場合は、括弧で短く添える
  （例: 「値が空の行は件数に数えない（空行を数えると欠落が隠れるため）」）。
- 既知の制約を固定するケースは、末尾に「（既知の制約）」と書く。

#### constraint_id の書き方

- 値は、その行の `function_name` の関数の `- 制約` に振られた**番号**（関数ごとに1から）。
  番号だけを書き、関数名や「制約」などの接頭辞は付けない（例: `2`）。
- **その行の関数の制約だけを指す。** 別の関数の制約を確かめている場合でも、その関数の番号は書かない
  （例: `readDocument` のケースが `readHeader` の制約も確かめていても、`readHeader` の番号は書かない）。
  別の関数の制約にしか対応ケースが無い場合は、その制約用のケースを制約を持つ関数に足すか、報告で挙げる。
- 1ケースで複数の制約を確かめる場合は、番号を小さい順にカンマ区切りで書く（例: `3,4`。CSV 上は `"3,4"` とクォートされる）。
- どの制約にも関係しないケース（フローの手順・対応表の行などだけを確かめるもの）は**空欄**にする。
- 設計書の制約に番号が振られていない（番号なしの箇条書き）場合は、`constraint_id` を書かずに、
  設計書の制約を番号付きにする必要があることを報告する。番号を推測で振らない。

#### 並び順と id

- 対象モジュールの行は、**関数一覧の順（呼び出し階層順）**に並べ、1つの関数の行は連続させる（途中に別の関数の行を挟まない）。
- 関数の中では、**`constraint_id` の小さい順**に並べる（上から順に制約1, 2, 3 … の対応ケースが並ぶようにする）。
  - 複数の番号を持つ行（`1,4`）は先頭の番号で並べ、同じ番号の中では単独の番号の行を先にする（`1` → `1,4` → `2`）。
  - `constraint_id` が空欄の行は、制約のある行の後ろにまとめる。
  - 同じ番号どうし・空欄どうしの中では、正常系の代表 → フローの手順順 → 対応表 → 性質 → 境界・異常 の順にする。
- `id` は既存の最大値 + 1 から連番で振る。**既存の行の `id` は振り直さない。**
- 行は CSV の**末尾に追記**する。既存の行の間に挿入しない。

#### 書き込み

CSV は文字列を手で連結せず、**クォートとエスケープを正しく扱える CSV ライブラリで書く**（クォートの崩れを防ぐため）。
スクリプトの言語は問わない（その環境で使えるものを選ぶ）。スクリプトはスクラッチパッドに置き、プロジェクトに残さない。

書き込みのスクリプトは次を満たすようにする。

- 列の順は `id, module_name, function_name, constraint_id, argument, expected_result, description`
- 文字コードは既存のファイルに合わせる（既定は UTF-8、BOM なし）
- 改行は既存のファイルに合わせる（既定は CRLF）
- クォートは必要な列だけ（カンマ・ダブルクォート・改行を含む値）。値の中のダブルクォートは `""` に二重化する
- 追記モードで開き、既存の行を書き換えない

追記の前に、既存ファイルの末尾が改行で終わっていることを確認する（終わっていなければ先に改行を足す）。
また、ヘッダー行の列が上の列の順と一致していることを確認する。
`constraint_id` 列が無い古い形式の CSV だった場合は、追記せずに止め、列の追加が必要なことを報告する。

### Step6. 既に行があるモジュールの場合（追加モード）

対象モジュールの行が CSV に既にある場合は、**既存の行を正として不足だけを足す**。

1. 既存の行を関数ごとに集め、Step3 の観点表・Step4 の制約と突き合わせる。
2. どの観点も満たしていない観点・制約だけを新しい行として追記する（`id` は最大値 + 1 から）。
3. 既存の行が設計書と食い違っている（期待値が現在の設計書と違う、関数名が設計書に無い）場合は、
   **書き換えずに報告する**。
4. 既存の行の `constraint_id` も同じく正として扱う。次の場合は書き換えずに報告する。
   - 番号がその関数の制約に存在しない（制約の削除・振り直しで外れた）
   - 番号の制約とケースの内容が合っていない
   - 制約を確かめているのに `constraint_id` が空欄になっている

### Step7. 自己点検する

書き終えたら、**追記した CSV を CSV ライブラリで読み直して**次を確認する。1つでも欠けていたら直してから報告する。

- [ ] 読み直した行数が「既存の行数 + 追記した行数」と一致している（クォートが崩れていない）
- [ ] すべての行が7列（`constraint_id` を含む）で、`id` に重複・欠番が無い（既存分の不備は直さず報告する）
- [ ] 関数一覧のすべての関数に、1件以上のケースがある
- [ ] `function_name` がすべて設計書の関数一覧に存在する
- [ ] `argument` の引数名が、その関数のシグネチャの引数名と一致し、必須の引数がすべて書かれている
- [ ] `argument` / `expected_result` の値が採用言語のリテラルで書かれている
- [ ] 各関数のフローの**境界・異常の手順**に対応するケースがある
- [ ] 各関数の**制約**のすべての番号が、その関数のいずれかの行の `constraint_id` に現れるか、「対応ケースなし」の理由がある
- [ ] `constraint_id` の番号が、すべてその行の関数の制約に実在する（別の関数の番号・存在しない番号を書いていない）
- [ ] `constraint_id` が番号のカンマ区切り（小さい順）か空欄になっている
- [ ] `expected_result` がすべて「expected_result の書き方」の形のどれかになっている
- [ ] 期待値の根拠が設計書（または依存先の設計書）のどこかに書かれている。**設計書に無い挙動を期待値にしていない**
- [ ] 戻り値のフィールド名がデータ定義の設計書と一致している
- [ ] 既存の行を1行も変更していない（`git diff` で追記だけになっていること）

### Step8. 報告する

- 追記した行数と `id` の範囲、関数ごとのケース数
- **制約と対応ケースの対応表**（関数ごと。制約の番号・文言 → `constraint_id` にその番号を持つ行の `id` の一覧、
  または「対応ケースなし」とその理由）
- **要確認リスト**: 設計書から期待値が一意に決まらず、書かなかった／弱い形で書いたケース（観点と理由）
- 設計書側の不備（フローに境界・異常の手順が無い、制約とフローの食い違い、制約に番号が無い、依存先設計書との矛盾）
- CSV 側の既存の不備（`id` 重複・欠番・クォート崩れ・設計書に無い関数名・実在しない `constraint_id`）
- 次にやるとよいこと
  - 「対応ケースなし」の制約のうち、観測できる形に言い換えられるものへのケース追加
  - この CSV をもとにテストコードを作る

## 決まっていないことの扱い

| 状況                                                       | 扱い                                                                                   |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 設計書（依存先を含む）から期待値が一意に導ける             | 導いて書く                                                                             |
| 戻り値の一部だけが導ける                                   | 導けるフィールドだけを列挙の形で書く                                                   |
| 期待値の形（空文字か値なしか、例外か空か）が決まらない     | **行を書かず要確認に回す**。仮の期待値で埋めない                                       |
| 観点は必要だが、設計書のフローに記述が無い                 | 行を書かず、「設計書に追加すべき記述」として報告する                                   |
| 設計書の記述どうしが矛盾している                           | どちらも採らず、矛盾として報告する                                                     |

## やらないこと

- **テストコード・プロダクトコードを書くこと。** CSV への追記までに留める（テストコードは後工程の役割）。
- **言語・テストの仕組みの決め打ち。** 基本設計・既存資産・ユーザーの回答に無い言語のリテラルやテストの書き方を前提にしない。
- **設計書に無い挙動の推測。** 「普通はこうなるはず」で期待値を作らない。要確認に回す。
- **既存の CSV の行の変更。** `id` の振り直し、並べ替え、書式の統一、不備の修正はしない。見つけたら報告する
  （ユーザーが直すと判断した場合のみ、依頼を受けてから直す）。
- **設計書の書き換え。** 制約の番号の振り直しも含め、依頼を受けてから行う。制約側にテストIDを書くこともしない。
- **他モジュールの責務をテストすること。** 設計書で「〜は`validator`が行う」とされている判断を、この関数のケースにしない。
- **実装に合わせたケースの作成。** 既存の実装があっても、実装の挙動を期待値として書き写さない。根拠は設計書だけとする。
