# 基本設計書作成スキル

`docs/design.md` を**テンプレートの構成**で書き起こし、そこで決めた設計判断を `docs/adr/000N-*.md` に残すスキルです。

このスキルがやるのは「**要件を読む → 未決定の論点を洗い出して確認する → 骨子を固める → 設計書とADRを書く → 自己点検して報告**」まで。
**モジュール設計書も実装コードも書きません。** 要件に無い設計判断を、ユーザーに確かめずに断定することもしません（→ 「やらないこと」）。

## 前提とするフォルダ構成

対象フォルダ（ユーザーが指定する。指定が無ければリポジトリのルート）配下:

```
{対象フォルダ}/
├── README.md                        … 要件（何を・誰のために・どう使うか）。このスキルの主な入力
├── docs/
│   ├── design.md                    … ★このスキルの生成先（基本設計）
│   ├── adr/
│   │   └── 000N-*.md                … ★このスキルの生成先（設計判断の記録）
│   ├── module/
│   │   └── {module}_design.md       … 後工程（generate-module-design）の生成先
│   └── test/
│       └── ut-test-design.csv       … 後工程（generate-ut-test-design）の生成先
├── {package}/                       … 実装先（このスキルでは触らない）
└── tests/{package}/                 … テストの置き場（このスキルでは触らない）
```

**この設計書は後工程のスキルの入力になる。** 特に次の節は、後工程が名指しで読みにいく。
欠けると後工程が止まるか、推測で書くことになるため、**必ず書く**。

| 節                     | 読むスキル                | そこから取るもの                                           |
| ---------------------- | ------------------------- | ---------------------------------------------------------- |
| モジュール構成         | `generate-module-design`  | 各モジュールの**責務の一文**（モジュール設計書の「背景・目的」の出発点） |
|                        | `generate-ut-test`        | **パッケージ名**（`tests/{package}/` のフォルダ名）         |
| 依存の向き             | `generate-module-design`  | 依存先と、**呼ばれる側／呼ぶ側**の関係                     |
| データフロー           | `generate-module-design`  | **どの値をどこで確定させるか**など、モジュールをまたぐ前提 |
| 残課題                 | `generate-module-design`  | 未決の論点の置き場所（後工程は勝手に追記せず報告する）     |
| 決定事項（ADRへのリンク） | `generate-module-design` | 「なぜそう決めたか」の出典                                 |

## 進め方

### Step1. 対象を確定する

1. 対象フォルダと**入力となる要件の文書**を確定する（既定は `README.md`）。**推測で決めない。曖昧なら確認する。**
2. `docs/design.md` が既にあるか確認する。
   - 無い、または空ファイル（0バイト）なら、そのまま書いてよい。
   - 中身がある場合は**上書き前に必ず読み**、手で書かれた記述を落とさないようにする。
     全面的に書き直すか、差分だけを直すかはユーザーに確認する。
3. `docs/adr/` にある既存のADRを読み、**採番の続き**と、既に決まっている判断を把握する。
4. `.claude/skills/` にある後工程のスキル（`generate-module-design` など）を確認し、
   **言語・テストの仕組みなど、スキルが前提にしているもの**を拾う（例: pytest 前提なら Python）。

### Step2. 入力を読む

書き始める前に、少なくとも次を読む。読まずに書かない。

| 入力                         | そこから取るもの                                                       |
| ---------------------------- | ---------------------------------------------------------------------- |
| 要件の文書（`README.md`）    | 目的、利用者、使い方の場面、記録・表示する項目、初期設定、将来やりたいこと |
| 要件の文書の「未決定」など   | **基本設計で決めなければならない論点**の一覧                           |
| 既存の `docs/adr/*.md`       | 既に決まっている判断（覆さない）                                       |
| `.claude/skills/*/SKILL.md`  | 後工程が前提にしている言語・フォルダ構成・設計書の形式                 |
| 既存の実装（あれば）         | 実際のモジュール分け。設計と食い違う場合は**書き換えず報告する**       |

要件の文書を読むときは、**使い方の場面（「ある1日」など）を1つずつ処理の流れに置き換えられるか**を確かめる。
置き換えられない場面は、論点として Step3 に回す。

### Step3. 論点を洗い出し、確認する

書き始める前に、要件から一意に決まらない論点を洗い出し、次の表で扱いを決める。

| 状況                                               | 扱い                                                                       |
| -------------------------------------------------- | -------------------------------------------------------------------------- |
| 要件の文書に「未決定」として明記されている         | **書く前にユーザーに確認する**。選択肢と推奨を添えて聞く                   |
| 決め方次第で、構成・データモデル・外部接続が変わる | **書く前にユーザーに確認する**（例: 実行環境、保存先、外部APIの有無）       |
| 妥当な選択肢が複数あり、どれでも全体が破綻しない   | 1つ選んで書き、**選んだ理由を本文に書く**。報告で要確認に挙げる           |
| 要件の文言と、実現上の都合が食い違う               | 都合に合わせて書き、**本文に理由を書いた上で残課題に挙げる**（例: 「月末に届く」→ 翌月1日に送る） |
| 本筋ではないが未決の論点                           | 設計書の「残課題」に ID を振って書く                                       |

- 確認は `AskUserQuestion` で、**1回にまとめて**聞く（最大4問）。各問に選択肢2〜4個と、推奨があれば先頭に `(推奨)` を付ける。
- 選択肢の説明には、**選ぶと何が変わるか**（手間・費用・後工程への影響）を書く。
- ユーザーの回答は、そのまま「決定事項」とADRに反映する。回答に理由が無ければ、ADRには選択肢の比較から導ける結果だけを書き、
  ユーザーの意図を創作しない。

### Step4. 骨子を先に固める

いきなり本文を書かない。次の順で確定させる。骨子はテンプレート（`templates/basic_design.md`）を使う。

1. **設計方針**: 要件の目的を1〜2文にし、判断に迷ったときの優先順位を3つ程度に言い切る
   （例: 「続けられるか」→「壊れても気づけるか」→「単純であるか」）。要件に判断基準が書かれていれば、それを最優先にする。
2. **決定事項**: Step3 で決まった論点を `論点 | 決定 | 記録` の表にする。記録列はADRへの相対リンク。
3. **システム構成**: 利用者・外部サービス・自分たちの部品と、その間のやり取りを `flowchart LR` で描く。
   プロセスの数と、書き込み元がいくつあるかを図の後に書く。
4. **モジュール構成**: 先に全モジュールを出し切る。
   - 列は `層 | モジュール | 責務`。**責務は1モジュール1文**で、「〜だけを行う」「〜を外に漏らさない」の形で境界が分かるように書く。
   - 層は「データ定義 → 純粋ロジック → 永続化 → サービス → 外部接続 → 起動」のように、依存の向きと同じ順で並べる。
   - データ構造を受け渡す専用のモジュール（`model` など）を1つ置く。後工程のデータ定義モジュール型の設計書になる。
   - **パッケージ名を表の前に明記する**。
5. **依存の向き**: `flowchart TD` で、モジュール構成の全モジュールの依存を描く。図の後に次を箇条書きにする。
   - 全員が参照してよいモジュール（`model` / `config` など。図では省略してよい）
   - 依存は一方向であること、下の層が上の層を知らないこと
   - **外部サービス・DBを呼んでよいモジュールの限定**（純粋ロジックは呼ばない）
6. **処理の流れ**: 要件の使い方の場面ごとに、`sequenceDiagram` と箇条書きで書く。
   登場するモジュールは、モジュール構成にあるものだけにする。
7. **データフロー**: `値 | 確定させる場所 | 決め方` の表。要件の「記録する項目」は**すべて**載せる。
   単位（円・JST など）、生の値と正規化した値のどちらを持つか、重複排除のキーもここで決める。
8. **データモデル**: テーブル（またはデータ構造）ごとに `列 | 型 | 必須 | 内容` の表と、不変条件を箇条書きで書く。
   列の細かい型や検証は、後工程のモジュール設計書に回してよい。その旨を節の冒頭に書く。
9. **方針の節**（必要な場合のみ）: 分類・通知など、複数のモジュールにまたがる決めごとは `## 〇〇の方針` として独立させる。
   ほかの節からはアンカーリンクで参照し、同じ説明を二度書かない。
10. **外部インターフェース・非機能・フォルダ構成・残課題**: テンプレートに沿って埋める。

### Step5. ADRを書く

Step3 で決まった論点ごとに、`docs/adr/{4桁の連番}-{英小文字とハイフンの短い名前}.md` を1本ずつ書く。
骨子は `templates/adr.md` を使う。

- **1本に1つの判断**。複数の論点をまとめない。
- 「背景」には、要件のどこで未決定だったかを書く（例: 「README『未決定』」）。
- 「選択肢」には、確認のときに示した選択肢をすべて書く。
- 「結果」には、**良くなること**と、**引き受けること（手間・制約）**の両方を書く。引き受けることのうち未決のものは、
  設計書の残課題の ID で参照する。
- 既存のADRを覆す判断になった場合は、既存を書き換えず、新しいADRを足して旧ADRの状態を「置き換え（ADR-000N）」にするようユーザーに提案する。

### Step6. 自己点検する

書き終えたら、**書いた設計書とADRを読み直して**次を確認する。1つでも欠けていたら直してから報告する。

- [ ] 見出し構成がテンプレートと一致している（該当しない節を消した場合は報告に書く）
- [ ] パッケージ名がモジュール構成の節に明記されている
- [ ] すべてのモジュールに**責務の一文**がある（2文以上になっていない）
- [ ] モジュール構成の表と、依存の向きの図のモジュールが**過不足なく一致**している
- [ ] 処理の流れ・データフローに出てくるモジュールが、すべてモジュール構成にある
- [ ] 依存の向きの図に、下の層から上の層への矢印が無い
- [ ] 要件の「使い方の場面」が、すべて処理の流れのどこかで説明されている
- [ ] 要件の「記録する項目」が、すべてデータフローとデータモデルに載っている
- [ ] 要件の「未決定」が、すべて決定事項か残課題のどちらかに載っている
- [ ] 要件の「将来やりたいこと」を、今回の設計に取り込んでいない（取り込まない前提が崩れないことだけ確かめる）
- [ ] 決定事項の各行が、実在するADRにリンクしている（ADRの無い行は「記録」列に出典を書いている）
- [ ] 要件と違う形にした箇所に、本文で理由が書かれ、残課題に挙がっている
- [ ] 他ファイルへのリンクが相対パスで、**実在するファイル**を指している
- [ ] mermaid の図が構文として正しい（ノードIDの重複・閉じ忘れが無い）
- [ ] 表がパイプ区切りで整形されており、列数が揃っている
- [ ] 実装コード・モジュール設計書の粒度の記述（関数のシグネチャなど）が入っていない

### Step7. 報告する

- 生成したファイルのパス（設計書とADR）
- 確認で決まった前提と、こちらで決めた前提（言語など、根拠付き）
- 設計書の要点（モジュールの数、依存の向きの方針、データフローで固定したこと）
- **要確認リスト**: 残課題のうち、ユーザーの判断が要るもの。要件と違う形にした箇所は必ず含める
- 次にやるとよいこと（例: `generate-module-design` で `model` の設計書から書く）

## やらないこと

- **モジュール設計書・実装コードを書くこと。** 関数のシグネチャやクラス定義は書かない（後工程の `generate-module-design` が書く）。
- **設計判断の捏造。** 要件の「未決定」や、構成を左右する論点を、確認せずに決めたように書かない。
  ADRに、ユーザーが言っていない決定理由を書かない。
- **要件の文書の書き換え。** 要件と設計の食い違いは、設計書の本文と残課題に書き、報告する。
- **将来やりたいことの先取り。** 要件の「将来やりたいこと」のための仕組み（複数ユーザー、タグなど）を今回の設計に入れない。
- **既存のADRの書き換え。** 覆す場合は新しいADRを足すよう提案する。
- **コミット。** ユーザーから頼まれるまで行わない。
