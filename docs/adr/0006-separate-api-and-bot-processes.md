# ADR-0006: REST API と Discord bot は別のプロセスで起動する

- 状態: 置き換え（[ADR-0007](./0007-bot-accesses-data-through-api.md)）
- 日付: 2026-10-19

## 背景

[ADR-0001](./0001-self-hosted-sqlite.md) では、Discord bot・REST API・定期実行を1つのプロセスに同居させると決めた。
書き込み元を1プロセスに限り、SQLite のロック競合を考えなくてよくするためである。

実装を進めると、1プロセスに同居させるための起動の処理が込み入ってきた。
uvicorn と discord.py はどちらも、自分でイベントループを持って戻らない起動の関数（`uvicorn.run()` / `client.run()`）を持つ。
同居させるには、両方を非同期の起動（`Server.serve()` / `client.start()`）に替えたうえで、片方が止まったらもう片方も止める後始末を自分で書く必要がある。
また、API を開発するときに uvicorn の自動リロード（`--reload`）が使えず、bot のトークンの誤りなど bot 側の失敗で API も止まる。

## 選択肢

1. 1つのプロセスに同居させる（ADR-0001 のまま）
2. REST API と、Discord bot＋定期実行を別のプロセスで起動する。どちらもサービス層と repository を import し、同じ SQLite のファイルを開く
3. 別のプロセスで起動し、bot と定期実行は REST API を HTTP で呼んで DB を操作する

## 決定

2 を採用する。

- 起動の入口を2つ持つ。REST API は `python -m tsukena.api`、Discord bot と定期実行は `python -m tsukena.bot` で起動する。1つにまとめて起動する `tsukena/main.py` は持たない。
- 定期実行（`scheduler`）は bot のプロセスに置く。Gmail の取り込み・週と月のまとめ・各通知は、どれも Discord に送る（`notifier`）ため、Discord への接続を持つプロセスで動かす。
- 記録のルール（支払日の計算・分類・重複排除・予算の判定・ルールの学習）はサービス層だけに置き、API と bot は同じ関数を呼ぶ。プロセスを分けても、入口によって振る舞いがずれないようにする。
- DB への接続（`repositories/database.py` の `connect()`）では、WAL モード（`journal_mode=WAL`）とロック待ちの時間（`busy_timeout`）を指定する。2つのプロセスからの書き込みが重なっても、すぐにエラーにせず待たせる。
- 月の予算など、もう一方のプロセスが変えうる設定は、起動時に1度だけ読んで持ち続けず、使うたびに DB から読む。

3 を選ばないのは、bot から現金を記録するための追加の API（`POST /transactions`）が要るためである。この API は、スマホアプリからの二重登録を防ぐため、わざと持たないことにしている（→ [design.md 4.3](../design.md#43-スマホアプリ修正確認待ち振り返り収入)）。
また、同じ機械の中で、関数を呼べば済む処理に通信と認証を挟むことになる。

## 結果

- 起動の処理がそれぞれ単純になる。2つのイベントループを同居させる処理と、片方が止まったときの後始末が要らない。
- API を `--reload` で開発でき、bot と API を別々に再起動できる。
- bot 側の失敗（トークンの誤り、Discord への接続の切断）で API が止まらない。逆も同じ。
- ログがプロセスごとに分かれる。
- SQLite への書き込み元が2つになる。ADR-0001 の「ロック競合を考えなくてよい」は成り立たなくなる。利用者が1人で書き込みはまれなため、WAL モードとロック待ちで足りるとみなす。重なりで待ちきれなかったときは、書き込みの例外として扱う。
- 常駐させる単位が2つになる。systemd などのユニットを2つ用意し、それぞれの再起動を設定する。
- 予算の到達の通知を1回だけ送る判定（`notification_log`）は、どちらのプロセスから記録しても DB の一意制約で守られる。
